# 埋点方案与指标体系

> 目标不是"埋很多点"，而是**用最少的点回答三个问题**：
> ① 供给够不够 ② 卡在哪个环节 ③ 成交快不快。

## 1. 指标体系

**北极星指标**：周成交订单数（Weekly Completed Orders）
→ 选它的理由：同时反映供给、需求、匹配与履约，且是双边市场的真实价值兑现；不像 UV / 发布数那样可以被单边刷高。

```
北极星：周成交订单数
├── 供给（能不能买到）
│   ├── 在售商品数（存量）
│   ├── 周新增商品数（增量）
│   └── 发布成功率 / 发布耗时
├── 需求（有没有人要）
│   ├── 周活跃买家数
│   ├── 商品详情 UV
│   └── 搜索成功率（有结果 / 总搜索）
├── 匹配（能不能谈成）
│   ├── 详情→会话率
│   ├── 会话→报价率
│   └── 报价接受率
└── 履约（能不能交付）
    ├── 下单→上传凭证率
    ├── 凭证→确认收款率
    ├── 双方确认完成率
    ├── 成交时长 P50 / P90
    └── 取消率 / 超时取消率
```

## 2. 交易主漏斗

| # | 环节 | 埋点事件 | 口径 | 观察点 |
| --- | --- | --- | --- | --- |
| 1 | 商品详情曝光 | `product_view` | 每次进入详情页 +1（同人同商品重复进入也计） | 供给是否被看见 |
| 2 | 发起会话 | `chat_open` | 首次创建会话才计，重复进入不计 | 商品吸引力 |
| 3 | 发送报价 | `quote_sent` | 每条报价消息 | 议价意愿 |
| 4 | 生成订单 | `order_created` | 卖家接受报价即建单 | 议价成交率 |
| 5 | 上传凭证 | `proof_uploaded` | 买家首次上传 | 支付意愿（最大流失点常见于此） |
| 6 | 确认收款 | `payment_confirmed` | 卖家确认 | 信任与响应速度 |
| 7 | 交易完成 | `order_completed` | 双方都确认 | 真实履约 |

**用法**：① 看整体转化；② 看**相邻环节比值**定位瓶颈。
例如"报价→订单"低说明卖家不愿让价；"订单→凭证"低说明买家反悔或不会扫码。

> 当前 Demo 里可以直接在浏览器控制台执行 `CFM.analytics.report()` 打印这张漏斗。
> 由于演示数据量小，绝对数值没有意义，看的是**链路是否被打通**。

## 3. 事件模型

### 3.1 命名与公共属性

- 命名：`对象_动作`，小写下划线，全小写；不使用驼峰、不使用中文
- 公共属性（所有事件自动携带）：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `e` | 事件名 | `order_created` |
| `t` | 客户端时间戳（ms） | `1763107200000` |
| `s` | 会话 ID（页面级） | `s_m3k2a1` |
| `u` | 用户 ID（未登录为 null） | `u_me` |
| `p` | 业务属性（白名单内） | `{order_id, amount}` |

### 3.2 事件表

| 事件 | 触发时机 | 业务属性 | 支撑指标 |
| --- | --- | --- | --- |
| `page_view` | 每次路由渲染 | `page` | 页面流量分布 |
| `product_view` | 进入商品详情 | `product_id, category, price, status` | 曝光、类目偏好 |
| `search` | 搜索输入（防抖后） | `keyword_len, category, result_count` | 搜索成功率 |
| `favorite_toggle` | 收藏/取消 | `product_id, on` | 意向强度 |
| `chat_open` | 首次创建会话 | `chat_id, product_id` | 详情→会话率 |
| `quote_sent` | 发送报价 | `chat_id, product_id, price, from_price` | 议价率、砍价幅度 |
| `quote_responded` | 卖家接受/拒绝 | `chat_id, accept` | 报价接受率 |
| `order_created` | 接受报价建单 | `order_id, product_id, amount` | 成交转化 |
| `proof_uploaded` | 买家上传凭证 | `order_id, amount, duration_ms` | 支付意愿、付款时长 |
| `payment_confirmed` | 卖家确认收款 | `order_id, amount, duration_ms` | 卖家响应速度 |
| `receipt_confirmed` | 单方确认收货/交付 | `order_id, role` | 履约推进 |
| `order_completed` | 双方确认完成 | `order_id, amount, duration_ms` | **北极星** |
| `order_cancelled` | 任一阶段主动取消 | `order_id, stage, reason_len` | 取消率与流失环节 |
| `order_expired` | 超时未付款自动取消 | `order_id, stage` | 流程阻力 |
| `product_published` | 发布成功 | `product_id, category, price, images` | 供给增量 |

## 4. 埋点实现（已落地）

代码在 [`src/analytics.js`](../src/analytics.js)，14 个事件挂在 `store.js`，1 个在 `router.js`。

四个刻意的设计：

1. **注册表即文档**：`REGISTRY` 里没登记的事件会被直接丢弃并告警
   → 防止随手埋点，也保证代码和本文档不会漂移
2. **属性白名单**：只保留注册表声明的字段
   → 从源头阻止手机号、聊天内容等敏感信息进入埋点
3. **采集点集中在 store 层**：业务写入只有一个入口，因此不会漏埋也不会重复埋
   → 页面层只负责 `page_view`
4. **全链路 try/catch**：埋点异常绝不影响交易主流程

本地只保留最近 500 条（`cfm.events.v1`），避免挤占 localStorage 配额；调试时设 `window.__CFM_DEBUG__ = true` 会实时打印事件。

## 5. 数据校验（上线前必做）

- [ ] 每个事件都能在 `REGISTRY` 找到，命名符合 `对象_动作`
- [ ] 属性只出现白名单字段，数值型字段类型正确（`amount` 是 number 不是 string）
- [ ] 同一 session 内 `page_view` 早于业务事件
- [ ] 漏斗各环节**单调递减**（不递减就是口径错了）
- [ ] `order_completed` 一单只出现一次（幂等）
- [ ] 取消/超时事件能区分 `stage`
- [ ] 断网、localStorage 满时，主流程不受影响

可在 CI 里直接跑：`npm test` 中的 `[13] 埋点与漏斗` 已覆盖注册表过滤、链路完整性、漏斗结构。

## 6. 看板设计

| 看板 | 图表 | 回答的问题 |
| --- | --- | --- |
| 供给健康 | 日新增商品（折线）、在售总量（折线）、类目分布（柱）、发布耗时 P50（折线） | 有没有东西可买 |
| 转化漏斗 | 七步漏斗（漏斗图）+ 详情→会话率、报价接受率（趋势） | 卡在哪一步 |
| 履约效率 | 成交时长 P50/P90（折线）、取消率与超时率（双轴）、分类目成交率（热力） | 交易顺不顺畅 |

看板使用建议：**先看漏斗定位环节，再看分维度拆解找原因**（类目 / 校区 / 新老用户）。

## 7. 隐私与合规

- 不采集：聊天正文、手机号、学号、图片内容
- `search` 只记录关键词长度，不记录原文
- `user_id` 为站内 ID，不含真实身份信息
- Demo 的埋点数据只存在浏览器本地，不上报任何服务器
- 若接入真实上报：需明示同意、支持退出采集、设定保留期限

## 8. 当前局限与下一步

| 局限 | 影响 | 下一步 |
| --- | --- | --- |
| 事件只在本地，无跨端 | 无法做真实大盘 | 接入轻量上报接口（批量 + 失败重试） |
| 无归因与用户分层 | 只能看整体转化 | 增加 `is_new_user`、`campus`、`source` 维度 |
| 无实时 | 无法做实时监控 | 写入消息队列后接实时看板 |
| 单校 demo 数据量小 | 绝对值无意义 | 造数 + 合成流量做压测 |
