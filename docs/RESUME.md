# 简历与面试怎么用这个项目

> 先说结论：**纯前端 Demo 在简历上属于「能写但不亮眼」**。要让它值钱，靠的不是页面多少，而是你能不能讲清楚「为什么这么设计」。这份文档给你可以直接用的写法，也告诉你短板在哪、怎么补。

---

## 一、先看真实数据（写简历别编）

| 指标 | 数值 |
| --- | --- |
| 页面 | 7 个主页面 + 4 个衍页面（登录、收藏、通知、他人主页） |
| 业务状态 | 商品 4 态、订单 4 态（含 2 个终态） |
| 消息卡片 | 5 类（报价/交货/收款码/凭证/订单） |
| 代码量 | JS ≈ 3.3k 行（12 个模块）、CSS ≈ 500 行 |
| 依赖 | 0（无框架、无构建、无第三方库） |
| 自动化测试 | 68 条断言（状态流转 + 16 个页面状态 + 埋点漏斗） |
| 站点体积 | 约 250KB（含全部演示图） |

## 二、三种写法，按篇幅选

### 1. 一行版（项目经历里只占一行时）

> **校园跳蚤市场**（个人项目 · 原生 JS）— 实现「发布→议价→下单→收款→交货→双方确认」的完整交易闭环，用状态机约束双端操作顺序，零依赖零构建，68 条自动化测试。

### 2. 三条要点版（推荐，绝大多数简历用这个）

> **校园跳蚤市场 · 二手交易平台** ｜ 个人项目 ｜ JavaScript / HTML / CSS
>
> - 独立设计并实现 7 个页面的完整交易闭环，把「谁该操作」抽象成**商品 4 态 + 订单 4 态双状态机**，避免双方在付款/交货环节互相等待
> - 业务逻辑全部收敛到单一 store 层（3.3k 行 JS、0 依赖），页面渲染为纯函数，**脱离浏览器即可断言每种状态的输出**，编写 68 条自动化用例并接入 GitHub Actions
> - 自研图片压缩链路（canvas 等比缩放 + JPEG 编码），把上传图从 MB 级压到 ~80KB，解决 localStorage 5MB 配额限制

### 3. STAR 版（面试自我介绍 / 作品集里展开）

- **S 背景**：校内二手交易靠微信群，消息刷屏、商品沉底、交易靠口头约定容易扯皮
- **T 任务**：做一个只服务本校的二手站点，要求身份可信、流程轻、**双方对「现在该谁操作」没有歧义**
- **A 行动**：
  1. 先写 PRD 定清 5 个模块的优先级与 8 条验收标准，再动代码
  2. 把交易流程拆成两套状态机，所有流转写成 store 层的守卫函数，UI 只负责展示
  3. 报价、收款码、凭证、交货信息做成**结构化消息卡片**（而非纯文本），让聊天记录本身成为交易凭证
  4. 用 Node 桩掉 DOM 跑业务回归，再接无头浏览器截图 + 控制台扫描兜底
- **R 结果**：7 个页面全流程可跑通；68 条用例覆盖状态流转；0 依赖、约 250KB；同类需求改动只动 store 层，页面基本不用改

## 三、面试官大概率会问的 8 个问题

**Q1：为什么不用 Vue/React？**
> 项目只有 7 个页面、状态集中在少数几个实体上，框架带来的构建链和抽象成本大于收益。我更需要的是「状态流转清晰」，所以把复杂度放在 store 层而不是框架层。当然如果要做多人协作或长期迭代，我会选 React + TypeScript。

**Q2：不用框架怎么管状态？**
> 单一 store + 页面栈。所有写操作都是 store 的方法，方法内部做校验和状态流转，然后页面整页重绘。聊天和列表会保存滚动位置。缺点是全量重渲染，优点是任何状态都能被复现和断言。

**Q3：订单和商品状态怎么保证不冲突？**
> 订单是主、商品跟随。比如只有「待付款」超时或任一方取消时，才把商品从「已预订」回滚到「在售」；「已完成」才会把商品写成「已售出」。这些守卫都写在 store 里，不依赖 UI 是否禁用按钮。

**Q4：双方确认收货怎么实现？**
> 订单上存 `buyerConfirmed` / `sellerConfirmed` 两个标记，`confirmReceipt()` 根据调用者角色写对应的一方，只有两个都为 true 才把订单置为完成、商品置为已售出。只点一方时订单仍停在「待交货」。

**Q5：超时取消是怎么做的？**
> 不用常驻定时器（页面关了就没了），而是「读时补偿」：下单时写入 `expiresAt`，每次启动和轮询调 `tick()` 扫描过期订单并取消。缺点是可能延迟几秒，但对这个场景够用。

**Q6：没有后端，数据怎么持久化？**
> localStorage。真正的坑是配额：原图直接存会立刻超限，所以上传时用 canvas 等比缩放到最长边 900、JPEG 0.75 编码，单张 60–100KB；写入时捕获 `QuotaExceededError` 并提示清理。

**Q7：怎么保证质量？**
> 两层：① `render()` 是纯函数，用 Node 桩掉 DOM 就能对每种状态断言输出，68 条用例覆盖状态流转；② 无头浏览器逐页截图并抓控制台异常——静态测试会漏「只在某个分支执行」的未定义变量，我就被 `timeShort` 坑过一次。

**Q8：如果要做成真产品，下一步改什么？**
> 后端（Node + SQLite 起步）→ JWT 登录 + 学校 CAS → WebSocket 做实时消息和未读 → 图片走对象存储 → 举报与申诉。前端把 store 拆成 domain/service 两层，逐步迁 TypeScript。

## 四、别这么写（容易翻车）

| 雷区 | 说明 |
| --- | --- |
| 写「高并发」「百万级」 | 纯前端 Demo 撑不起这种词，一问就露 |
| 罗列技术栈 | 「HTML/CSS/JS/LocalStorage」不像优势，像清单 |
| 只说「实现了 7 个页面」 | 页面数量不是价值，**流程闭环和状态设计**才是 |
| 不提取舍 | 面试官最想听的是「你为什么不用 X」 |
| 放不了链接 | 简历上不给可访问地址，等于让 HR 相信你 |

## 五、让它再加分的 3 件事

1. **上线一个可访问的 Demo 链接**（仓库已带 Pages 工作流，见 README），简历直接放 URL
2. **录一段 40 秒 GIF** 走完一次完整交易，放在 README 顶部（工具：ScreenToGif / Kap）
3. **按岗位补短板**：
   - 投前端：把 `store.js` 迁 TypeScript、加 ESLint + Vitest
   - 投全栈：补 Node API + SQLite + JWT，把 localStorage 换成 HTTP，这个项目立刻从「Demo」变成「系统」
   - 投产品：把 PRD 扩成完整竞品分析 + 数据埋点方案，代码只是佐证

## 六、如果投产品岗

同一份作品，投产品要换一套讲法：**弱化技术栈，强化判断过程**。

### 简历三条（产品向）

> **校园二手交易平台** ｜ 个人项目（独立完成从需求到落地）
>
> - 通过竞品分析确认「高交易闭环 × 高同校匹配」是市场空白，据此把产品收敛为「只做本校 + 结构化交易状态」，**主动砍掉平台支付、评价体系、推荐算法**三项重功能并说明代价
> - 设计商品 4 态 + 订单 4 态双状态机，把线下「口头约定」变成可追踪的系统状态，覆盖取消、超时等 6 条异常分支，直接消灭「钱付了没 / 东西给了没」的扯皮
> - 定义北极星指标（周成交订单数）与七步交易漏斗、15 个埋点事件，并在代码中落地（注册表约束 + 属性白名单），可现场演示漏斗输出

### 产品面试大概率会问的 6 个问题

**Q1：你怎么确认这个需求是真的？**
> 校园二手在微信群已经自发形成交易，说明需求存在；痛点不在「找不到人」而在「约好之后」——谁先付、何时交货、付了没，全靠口头。我的产品判断因此落在「结构化交易状态」而不是「更好的聊天」。

**Q2：为什么不做平台支付？**
> 两条：资金合规成本不是学生项目能承担的；抽佣会显著降低使用意愿。替代方案是「线下扫码 + 上传凭证 + 卖家确认」，代价是依赖双方诚信，所以我又加了双方确认收货作为终态约束。

**Q3：北极星为什么是「周成交订单数」而不是 GMV 或 DAU？**
> GMV 在校园场景客单价低、单笔高价即可拉高，容易被污染；DAU 是过程指标。成交订单数同时反映供给、需求、匹配和履约，是双边市场真正的价值兑现。

**Q4：怎么冷启动？**
> 先解决供给密度：切入点是毕业生宿舍楼，用「代发布」把存量搬上来；单校在售低于约 200 件时买家搜三次没结果就会流失。然后是发布成本（60 秒内完成）和首单体验（前期人工陪跑）。

**Q5：闲鱼为什么不做这块？**
> 不是不能，是不值得：校园盘子小、需要极高地理密度、与主站「同城/跨城」定位冲突，且学生群体的支付与信用体系已经能复用。这恰好是小团队的窗口。

**Q6：上线后你看哪个指标？某一步掉了怎么排查？**
> 先看七步漏斗定位卡点，再看「相邻环节比值」。例如报价→订单低说明卖家不愿让价，就去查报价分布与标价偏离度；订单→凭证低说明买家反悔或不会扫码，去看取消原因与超时率。拆解维度按类目、校区、新老用户逐层下钻。

### 一个提醒

产品岗看的是**判断力**：能说清「不做什么、为什么不做、代价是什么」，比列出做了多少功能更有说服力。这份项目里最能打的部分是 `docs/COMPETITIVE.md` 第 7 节（取舍表）和 `docs/ANALYTICS.md` 第 2 节（漏斗口径）。
